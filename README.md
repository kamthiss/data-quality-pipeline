# data-quality-pipeline

Пайплайн загрузки заказов, который замечает собственные ошибки и не публикует испорченную витрину.

**Бизнес-вопрос:** как понять, что отчёт обновился некорректно, раньше, чем на него посмотрит руководитель?

## Как устроено

```
API → raw → кандидат → проверки → staging → витрина
                          │
                          └─ ошибка: витрина не меняется, код выхода 1
```

Источник — локальный API заказов маркетплейса с переключаемыми сбоями. Каждый запуск перезагружает последние 7 дней, проверяет кандидата и публикует витрину «выручка по дням и городам», только если прошли все блокирующие проверки. Результат каждой проверки записывается в базу.

Правила описаны в [docs/data_contract.md](docs/data_contract.md): 12 блокирующих проверок и 6 предупреждений. Контракт закоммичен первым, до кода.

## Сценарии сбоев

Для каждого сбоя исход записан заранее, `make scenarios` проверяет, что пайплайн ведёт себя именно так.

| Сценарий | Что случилось | Исход |
|---|---|---|
| clean | всё нормально | опубликовано |
| rerun | тот же день дважды | опубликовано, витрина не изменилась |
| duplicates | 22 заказа пришли дважды | опубликовано, предупреждение W01 |
| api_500 | две ошибки сервера подряд | опубликовано после повторов |
| api_down | источник лежит | код 2, витрина вчерашняя |
| partial_page | ответ 200, но страница пустая | заблокировано B08 |
| missing_day | день пустой | заблокировано B09, B10, B11 |
| schema_drift | поле переименовано | заблокировано B01 |
| bad_values | отрицательные суммы, неизвестный статус | заблокировано B04, B05 |
| late_data | 40 заказов пришли через два дня | опубликовано, W04, прошлый день пересобран |
| volume_drop | источник сам потерял 40% заказов | опубликовано с предупреждением W05 |

После каждого сбоя источник возвращается в норму, запуск повторяется, и витрина совпадает с эталонной.

Два сценария важнее остальных. В partial_page объём падает только до 68% от обычного, и остановить публикацию может лишь сверка с контрольным итогом источника. В volume_drop источник теряет данные и сходится сам с собой, поэтому проверки могут только предупредить. Это граница того, что можно поймать без второго независимого источника.

## Запуск

Нужны Docker и uv.

```
uv venv --managed-python --python 3.12 .venv
uv pip install --python .venv/bin/python -e .
make demo        # чистый прогон за август и сентябрь 2026
make scenarios   # 11 сценариев сбоев, около полутора минут
make test-all    # 71 тест
```

Postgres работает на порту 5435, API — на 8040.

## Что внутри

- `src/dqpipe/source/` — генератор данных и API со сбоями
- `src/dqpipe/run.py` — загрузка и шлюз публикации
- `src/dqpipe/checks.py` — проверки, каждая одним SQL-запросом
- `src/dqpipe/freshness.py` — монитор свежести
- `src/dqpipe/scenario.py` — сценарии сбоев
- `docs/runbook.md` — что делать при каждом исходе
- `docs/questions.md` — вопросы по проекту и ответы
