# Контракт данных и правила качества

Документ написан до кода. Он фиксирует, какие данные мы ждём от источника, что считаем ошибкой и что происходит с витриной, если ошибка найдена. Код и тесты проверяют именно эти правила.

## Источник

API заказов маркетплейса отдаёт заказы за один день по страницам:

- `GET /orders?date=YYYY-MM-DD&page=N` — страница до 500 заказов, в ответе есть номер страницы и общее число страниц;
- `GET /orders/summary?date=YYYY-MM-DD` — контрольный итог за день: число уникальных заказов и сумма `amount_rub` по последним версиям заказов.

Все время в API в UTC. Отчётный день считается по московскому времени: заказ, созданный 31 августа в 22:30 UTC, относится к 1 сентября.

## Поля заказа

| Поле | Тип | Правило |
|---|---|---|
| order_id | текст | обязательно, бизнес-ключ |
| created_at | время UTC | обязательно |
| updated_at | время UTC | обязательно, не раньше created_at |
| customer_id | текст | обязательно |
| city | текст | может быть пустым |
| status | текст | created, paid, cancelled, refunded |
| amount_rub | число, 2 знака | больше 0 и не больше 300 000 |
| items_count | целое | от 1 до 50 |
| payment_method | текст | card, sbp, cash_on_delivery |

## Повторы одного заказа

Один и тот же order_id может прийти несколько раз, и это не всегда ошибка: статус заказа меняется. Правила:

- полностью одинаковые строки — дубль, оставляем одну, пишем предупреждение;
- тот же order_id с более поздним updated_at — новая версия заказа, она заменяет старую;
- тот же order_id и тот же updated_at, но разные данные — конфликт, сборка останавливается.

## Витрина

`mart.daily_revenue` — одна строка на отчётный день и город:

- orders_created — число заказов, созданных в этот день;
- orders_paid — сколько из них сейчас в статусе paid;
- revenue_rub — сумма amount_rub по заказам в статусе paid; возвраты и отмены в выручку не входят;
- cancel_rate — доля отменённых.

Пустой город в витрине показывается как «не указан».

## Блокирующие проверки

Если нарушено хотя бы одно правило, витрина не обновляется: руководитель видит последнюю корректную версию.

| Код | Проверка |
|---|---|
| B01 | все поля на месте и приводятся к своим типам |
| B02 | order_id, created_at, updated_at, customer_id не пустые |
| B03 | после удаления дублей order_id уникален, конфликтов версий нет |
| B04 | status из допустимого списка |
| B05 | amount_rub в диапазоне |
| B06 | items_count в диапазоне |
| B07 | updated_at не раньше created_at |
| B08 | число заказов и сумма совпадают с контрольным итогом API |
| B09 | в загруженном периоде нет пропущенных дней |
| B10 | последний опубликованный день — вчерашний |
| B11 | заказов за день не меньше 50% медианы предыдущих 7 дней |
| B12 | итоги витрины совпадают с итогами staging |

## Предупреждения

Публикация идёт, но в отчёте о запуске есть запись.

| Код | Проверка |
|---|---|
| W01 | удалены точные дубли (сколько) |
| W02 | пустой город больше чем у 1% заказов за день |
| W03 | появился новый город или способ оплаты |
| W04 | пришли заказы за уже опубликованные дни, эти дни пересобраны |
| W05 | заказов за день от 50% до 80% медианы предыдущих 7 дней |
| W06 | есть заказы дороже 100 000 ₽ |

Способ оплаты не входит в блокирующие: новый способ не делает выручку неправильной, а остановить из-за него отчёт хуже, чем показать его с пометкой.

## Свежесть и качество — разные вещи

Проверка свежести (B10) отвечает на вопрос, пришли ли данные вовремя. Проверки качества (остальные) — правильные ли они. Свежие данные могут быть испорчены, а корректные — устаревшими. Нужны обе.

## Успешный запуск не значит правильная витрина

API может ответить кодом 200 и при этом недодать страницу. Скрипт завершится без ошибок, но выручка будет занижена. Такой случай ловит сверка с контрольным итогом (B08) и проверка объёма (B11).

## Поведение при запуске

- Запросы к API: таймаут 10 секунд, до 3 повторов с паузой 1, 2 и 4 секунды.
- Код выхода: 0 — опубликовано (возможно, с предупреждениями), 1 — остановлено проверкой, 2 — источник недоступен.
- Сырые ответы сохраняются в raw без изменений, с номером загрузки. Поэтому день можно пересобрать без повторного обращения к API.
- Загрузка дня идемпотентна: повторный запуск за тот же день заменяет его данные в staging, а не добавляет к ним.
- Витрина пересобирается в транзакции и подменяется только после прохождения блокирующих проверок.
- Каждый запуск и результат каждой проверки записываются в meta, вместе с примерами нарушающих строк (до 20).

## Уточнения после реализации

Этот раздел дописан после того, как код был написан и проверен на сценариях сбоев. Правила выше не менялись. Ниже — решения, которых в первой версии не было или которые оказались неоднозначными.

- Код выхода 3 — непредвиденная ошибка самого пайплайна, статус error. При коде 1 сломаны данные, при коде 3 — код или окружение. Запуск не должен оставаться в статусе running; если всё же остался (например, упала база), его находит монитор свежести.
- Окно загрузки — 7 дней до отчётного дня включительно. Возвраты приходят до 5 суток спустя. Если загружать только вчерашний день, выручка прошлых дней останется завышенной, и ни одна проверка этого не заметит.
- payment_method может быть пустым. Пустое значение считается «вне списка» и даёт предупреждение W03, а не ошибку.
- W04 срабатывает только на новые заказы за уже опубликованные дни. Смена статуса известного заказа, например возврат, — нормальное обновление. Иначе предупреждение горело бы при каждом запуске, и его перестали бы читать.
- Если не прошла B01, проверки, которым нужны типизированные поля, получают статус skipped: нельзя проверить диапазон суммы, если колонки суммы нет.
- B11 и W05 пропускаются для дня, у которого меньше 3 предыдущих дней истории.
- B10 проверяется в двух местах: внутри запуска (в данных есть отчётный день) и отдельным монитором свежести (витрина не устарела на сегодня). Монитор нужен потому, что при недоступном источнике пайплайн просто ничего не публикует.
- Отдельной команды пересборки из raw без обращения к API нет. Восстановление — повторный запуск за последний день: окно перезаберёт все затронутые дни. Raw хранится для разбора: что именно прислал источник в момент сбоя.
